## 1. 🔴 Блокирующее расхождение: методичка не соответствует обсуждённому

Официальная методичка ПЗ2 в проекте называется **«Анализ продольного профиля и плана трассы ВСМ-1 для определения максимально возможной скорости движения»**. Это 18 слайдов: уклоны не более 24‰, радиусы вертикальных кривых по формуле `Rв = (Vmax/3,6)² / aв`, радиусы круговых кривых (10 000 м при 400 км/ч, 7 500 м при 350 км/ч, 5 500 м при 300 км/ч, 3 800 м при 250 км/ч в исключительных случаях), возвышение наружного рельса до 150 мм, определение ограничивающего фактора.

**На встрече 02.09 обсуждалось совершенно другое:** типы строительных работ, замер длин линейкой по карте, разбиение трассы на пространственные этапы, диаграмма Ганта, критический путь, распределение рабочих, отчёт по материалам и машино-часам. Ни один из этих терминов в методичке ПЗ2 не встречается. Ни одна из восьми методичек проекта не описывает организацию строительства.

**Возможные трактовки — выбрать должен заказчик, не мы:**

1. Обсуждавшийся модуль **заменяет** существующий ПЗ2, методичка устарела и будет переписана.
2. Это **новый модуль** (ПЗ9 или отдельная дисциплина Михаила / Ольги Владимировны / Артёма Глебовича), которому по ошибке присвоен номер 2.
3. Модуль **дополняет** ПЗ2: сначала анализ профиля и плана, затем организация строительства в одном задании.

**Вопрос заказчику формулируется так:** методичка ПЗ2 описывает анализ профиля и плана трассы — она заменяется тем, что мы обсуждали 02.09, или это разные задания? Если заменяется, нужна новая методичка; если нет, нужен её номер и место в графе зависимостей.

> До ответа документ ниже описывает **обсуждённый на встрече модуль**, условно называемый ПЗ2 — так, как его назвал заказчик. Действует правило проекта: слово заказчика приоритетнее, противоречия фиксируются, а не разрешаются молча.

## 4. Модель данных

### 4.1 Работа (`Work`)

Основная сущность модуля. Создаётся студентом, накапливается в общем пуле, затем распределяется по этапам.

```ts
type WorkKind =
  | 'existingLineRepair'   // Ремонт существующей линии
  | 'ballastTrack'         // Балластный путь
  | 'earthworks'           // Земляное полотно
  | 'viaduct'              // Эстакада
  | 'bridge'               // Мост
  | 'tunnel'               // Тоннель
  | 'turnout';             // Стрелочный перевод

interface Work {
  id: string;
  kind: WorkKind;
  lengthKm: number | null;   // null для точечных объектов, см. §11 в-3
  stageId: string | null;    // default null — работа в общем пуле
  conditions: SoilCondition[];
}

type SoilCondition = 'weakSoil' | 'rocky';  // формулировка второго — см. §11 в-2
```

**Семантика типов.** Ремонт существующей линии — когда ВСМ идёт по существующим путям с заменой подстанций, отдельная стоимость. Земляное полотно — высокая насыпь для сохранности, устойчивости и выравнивания рельефа. Балластный путь — щебёночное основание вместо бетонной плиты: укладывается быстро, требует постоянного обслуживания. Стрелочный перевод марки **1/25** — очень пологий, восемь приводов, считается отдельно от прочих работ.

**Дополнительное условие** влияет на состав работ: слабые грунты требуют забивки свай до твёрдого слоя с устройством ростверка.

### 4.2 Этап (`Stage`)

**Этап пространственный, не временной.** Трасса делится на участки, которые строятся параллельно. Для строящейся ВСМ Москва — Санкт-Петербург их, по разным репликам на встрече, семь или девять; точное число несущественно.

```ts
interface Stage {
  id: string;
  title: string;      // произвольное название, вводится студентом
  order: number;
}
```

## 5. Экран 1 — Работы и линейка

### 5.1 Карта

Переиспользуется компонент карты из ПЗ1 вместе с проложенной трассой. Трасса приходит через JSON-мост, заново не строится.

**Режимы карты:** «Просмотр» и «Линейка» (в ПЗ1 было «Просмотр / Станция / Линия трассы / Центр»). Клавиша `Esc` возвращает карту в «Просмотр» — та же механика, что уже реализована в ПЗ1 (П-04), переиспользовать.

**Инструмент «Линейка» (планиметр).** Студент прикладывает линейку к готовой трассе и измеряет длину участка. Заказчик оценил этот инструмент как единственную технически нетривиальную часть экрана: «самое тяжёлое — это линейка, потому что все остальные инструменты здесь — это таблица с подачей формы».

Реализация: последовательность кликов по карте, расстояние считается **геодезически (гаверсинус)**, не по Web Mercator — систематическая ошибка на широтах России, решение зафиксировано в ПЗ1 и распространяется сюда.

### 5.2 Таблица работ

Таблица со строками и кнопкой ⊕ для добавления. Каждая строка: тип работы (выбор из списка §4.1) и длина. Длина заполняется вручную после замера линейкой — автоперенос из линейки в поле на этом этапе не требуется, но допустим.

### 5.3 Проверка длины

Сумма длин всех линейных работ сверяется с **длиной маршрута, полученной из JSON ПЗ1**. Замеры линейкой заведомо неточны, студент должен видеть расхождение и добить длины руками до совпадения.

Отображение: сумма замеров, эталонная длина из ПЗ1, расхождение. Допуск не определён (§11 в-5). До определения допуска — **показывать расхождение, но не блокировать переход**.

**DoD экрана 1:** карта с трассой из ПЗ1 отображается; линейка измеряет расстояние геодезически; работы добавляются, редактируются и удаляются; сумма длин сверяется с эталоном; состояние сохраняется в JSON-мост.

## 6. Экран 2 — Разбиение на этапы

Слева таблица этапов с кнопкой ⊕: при нажатии открывается мини-форма ввода названия. Справа — пул всех работ, созданных на экране 1. Каждая работа отображается карточкой с типом и длиной.

**Взаимодействие — drag-and-drop.** Перетаскивание карточки работы в строку этапа проставляет ей свойство `stageId`. По умолчанию `stageId = null`, и работа лежит в общем пуле. Работа может быть перетянута обратно в пул или в другой этап.

Заказчик описал это как перекидываемые карточки в духе доски задач и специально отметил, что техническая реализация не принципиальна: важно, что после перетаскивания у работы появляется принадлежность этапу.

**DoD экрана 2:** этапы создаются с произвольным названием; работы перетаскиваются между пулом и этапами в обе стороны; `stageId` сохраняется в JSON-мост; работа не может принадлежать двум этапам одновременно.

## 7. Экран 3 — Упражнения

### 7.1 Упражнение Ольги Владимировны — выравнивание работ

**Код уже существует.** Это тренажёр КСГ (календарно-сетевой график), который, по словам заказчика, «в ПЗ-2 уже вбит». Механика в нём есть: работы двигаются, ресурсы перераспределяются, считаются человеко-часы и трудоёмкость.

> [!important] Пересмотр оценки репозитория
> Ранее ветка `merge_map_ksg_last` числилась риском загрязнения от постороннего проекта КСГ. Это неверно: КСГ — легитимная часть ПЗ2. Ветку **не удалять**, содержимое разобрать и инвентаризировать до 15.09.

Заказчик просил **не показывать этот тренажёр никому до готовности**, чтобы не получить вопросов, почему он выглядит не так, как задумано в финале.

**Задача на этап A:** инвентаризировать существующий код КСГ, подключить как есть, не переписывать.

### 7.2 Упражнение Артёма Глебовича — критический путь

Самое дешёвое в реализации упражнение модуля. Студенту показывается **готовая сетевая диаграмма в виде PNG**, он определяет критический путь и вводит ответ. Ответ сверяется с заранее известным эталоном — правильно или нет.

Диаграммы предоставляет заказчик: «таких диаграмм я вам 3-4 сделал, они есть в настоящей ВСМ». Формат ответа и эталоны — см. §11 в-8.

**Обновление после передачи упражнения.** Заказчик прислал семь вариантов в виде таблиц работ, без PNG. Локальный прототип строит сеть из указанных зависимостей и проверяет ранние сроки, срок проекта и полный набор критических путей; поздние сроки и резервы доступны для дополнительной проверки. Ключ вариантов 6 и 7 расходится с таблицами — см. [`pz2-critical-path-data.md`](./pz2-critical-path-data.md). Прежнее описание PNG выше оставлено как история исходного ТЗ.

Контекст для формулировки задания: критический путь — цепочка работ наибольшей длительности, он может меняться по ходу проекта; работы вне критического пути имеют запас и могут отставать без последствий для срока.

**DoD экрана 3:** тренажёр выравнивания открывается и работает; сетевая диаграмма отображается, ответ вводится и проверяется по эталону; результат сохраняется в JSON-мост.

## 8. Экран 4 — Ресурсный график и диаграмма Ганта (этап B)

**Требования не определены.** Заказчик о содержательной части этого экрана: «что здесь делать, на самом деле хрен его знает». Всё, что обсуждалось про перераспределение освободившихся рабочих между этапами, — размышления вслух нескольких участников, не согласованное требование.

Зафиксировано только направление:

- Гант строится по этапам: строки — этапы, внутри работы в порядке выполнения
- Этапы выполняются параллельно, сложность у них разная
- Количество рабочих фиксировано на весь проект, студент распределяет их между этапами
- Критерий качества — равномерная загрузка во времени: считается хорошим результатом, когда потребность в людях постоянна и не приходится набирать и распускать бригады
- На доске присутствует легенда «Люди» и «куп. тех.» и подпись, читаемая как «Нач. раб.» — расшифровка не подтверждена

### 🔴 Незакрытый пробел: длительности работ

**Диаграмма Ганта требует длительность каждой работы. Ни один источник её не определяет.** У работы есть только тип и длина. Длительность может быть выведена как `трудоёмкость(тип) × длина / число рабочих`, но нормативы трудоёмкости на километр по типам работ отсутствуют, а зависимость длительности от числа назначенных людей заказчиком не обсуждалась.

Без этого экран 4 не проектируется. Вопрос вынесен в §11 в-6 и должен быть задан до начала этапа B.

**На этап A ничего по этому экрану не делается.**

## 9. Отчёт (этап B)

Состав: израсходованные материалы, человеко-часы, машино-часы.

**Источник данных согласован необычным образом и это зафиксировано намеренно.** Заказчик, чтобы не задерживать команду, разрешил сгенерировать нормативы нейросетью: на каждый тип работы 3-4 подработы, 2-3 материала, 1-2 машины плюс человеко-часы, всё в расчёте на километр. Дальше значения умножаются на длину.

Данные заведомо черновые. Их выверит эксперт Вадим, привлечённый заказчиком. **Точность на этапе разработки не является нашей зоной ответственности**, но сгенерированные значения должны быть вынесены в отдельный конфигурационный файл с явной пометкой, что это временные данные, подлежащие замене.

## 10. JSON-мост

Связь ПЗ1 → ПЗ2 сильнее, чем зафиксировано в `architecture.md` (там значится слабая связь, только паспорт). Фактически переносятся:

- паспорт проекта (учебная группа, вариант)
- **длина маршрута** — эталон для проверки длины (§5.3), заказчик указал явно: «надо будет забрать из JSON-а прошлого и сюда выводить»
- геометрия трассы и станции — для отрисовки карты на экране 1

Требуется повышение `schemaVersion` до `1.2` с добавлением секции `pz2` и обратной совместимостью: файл версии 1.1 должен открываться. Раздел `progress` для восстановления позиции внутри модуля — по образцу ПЗ1, адресация шага стабильным идентификатором, не номером.

**Обновить `docs/architecture.md`:** ребро ПЗ1→ПЗ2 переклассифицировать из слабого в сильное с перечнем переносимых величин.

## 12. Правила разработки

Действуют без изменений правила проекта, зафиксированные в `CONTRIBUTING.md`:

- Бэкенда нет. Только статическая сборка, персистентность через JSON-файл, никакого localStorage
- Производные величины — только через селекторы
- Каждая расчётная функция сопровождается тестом на примере из методички
- Каждый тикет — отдельный коммит
- Дизайн строго по `docs/design-reference.html`, цвета на глаз не подбираются
- Компоновка под iframe iSpring: `overflow-hidden` на корне, внутренние списки скроллятся изолированно, двойного скролла быть не должно
