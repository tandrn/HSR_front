# Архитектура — техническое ядро

См. также: [design-system.md](./design-system.md) · [pz-specs.md](./pz-specs.md) · [open-questions.md](./open-questions.md)

## Стек

- React 19 + TypeScript + Vite. Тесты — Vitest.
- Стилизация — обычный CSS с custom properties. **Tailwind и Framer Motion не подключены.** Добавление — отдельное решение, фиксировать здесь явно.
- **Бэкенда нет.** Никакого Django/Postgres/Docker-compose. Причина: преподаватель проверяет работы вручную по PDF, аккаунты и роли не нужны. Деплой — статическая сборка `vite build` за одним Caddy/Nginx.
- Пакеты к подключению: `maplibre-gl` (карта ПЗ1), `katex` (формулы — рендер проверен вручную через CDN, рисков с Vite не ожидается), `@react-pdf/renderer` (PDF-отчёт).

### Внешние сервисы времени выполнения

Бэкенда нет, но два сервиса OSM приложение вызывает из браузера напрямую. Оба нужны только на экране карты ПЗ1, оба деградируют мягко — без сети остальные шаги работают. Больше внешних вызовов во время работы нет: шрифт Raleway лежит в сборке (`@fontsource`), а не тянется с Google Fonts — модуль открывают в аудитории внутри iSpring, и недоступный CDN молча подменял бы весь визуальный язык системным шрифтом.

| Сервис | Зачем | Что при недоступности |
|---|---|---|
| `tile.openstreetmap.org` | подложка карты | карта пустая, точки ставятся и считаются как обычно |
| `nominatim.openstreetmap.org` | определение субъекта РФ по координатам станции | поле региона не заполняется автоматически, остаётся ручной ввод со справочником |

**Про Nominatim — решение и его цена.** Офлайн-альтернативы нет: границ субъектов в проекте не заведено, а составлять их приближённо означало бы подставить выдуманные числа, что правила проекта запрещают. Условия использования сервиса — не чаще одного запроса в секунду; в коде стоят очередь с интервалом 1,1 с, кэш по округлённым координатам и запрос только при фактическом изменении координат станции. Риск, о котором надо помнить: класс за одним NAT-адресом делит лимит на всех, поэтому автозаполнение спроектировано как подсказка, а не как источник истины — поле всегда остаётся редактируемым.

## Структура репозитория

```
src/
  app/                  — корневая оболочка, точка входа
  modules/
    pz1/
      steps/            — компоненты шагов конкретного ПЗ
      variants.ts        — статические пресеты вариантов (если есть у ПЗ)
      slides.ts           — типизированный контент теории
      types.ts             — PzNResult и внутренние типы модуля
      index.tsx
    pz3/ … pz8/           — та же структура (пока реализован pz3/)
  shared/
    ui/                    — переиспользуемые компоненты (кнопки, инпуты, табличные примитивы, прогресс-трасса)
    lib/                     — чистые расчётные функции, без React
    hooks/
    types/
  bridge/
    schema.ts               — Passport, BridgeSchema, PzNResult union
    context.tsx               — ModuleStateProvider (см. «Состояние» ниже)
    io.ts                       — экспорт/импорт JSON моста
  pdf/
    templates/
    render.ts
docs/
  architecture.md
  design-system.md
  pz-specs.md
  open-questions.md
  examples/                  — тестовые фикстуры из методичек, по одному файлу на ПЗ
    pz1-passenger-flow.md      — модель прогноза пассажиропотока ПЗ1 (формулы, константы, контрольные числа)
    pz4.md, pz6.md             — вариантные таблицы и контрольные расчёты
    pz7-matrix.md              — шахматка пассажиропотоков ПЗ7
  pz1-copy-and-validation.md — тексты интерфейса и правила валидации ПЗ1 (не фикстура, поэтому не в examples/)
  pz1-station-route-binding.md — объяснение логики привязки станции к трассе для заказчика
```

Имя файла фикстуры — по содержанию, не строго `pzN.md`: шаблон `pzN.md` в ссылках других
документов читать как «файл фикстур этого ПЗ в `docs/examples/`». Фикстуры остальных ПЗ пока
не заведены — их нет, а не лежат где-то ещё.

**Правило:** код одного ПЗ не импортирует код другого ПЗ напрямую. Переиспользуемая логика/UI выносится в `shared/`.

## Состояние приложения

- Локальное состояние одного шага — `useState`/`useReducer` внутри компонента шага.
- Состояние модуля целиком (массив шагов, текущий шаг, введённые данные до экспорта в мост) — один React Context на модуль (`ModuleStateProvider` в `bridge/context.tsx`), инициализируется из моста при входе в модуль.
- **Текущий шаг и ссылки между шагами — по стабильному идентификатору (`stepId`), не по числовому индексу/позиции в массиве.** Порядок шагов должен меняться без последствий для уже сохранённого прогресса (прецедент: ПЗ1, шаги «Прочие параметры»/«Частота+Стоимость» поменялись местами в процессе разработки).
- Мост — обычный объект/файл (`bridge/schema.ts` + `bridge/io.ts`), не React state, не завязан на рендер-цикл. Модуль читает его на входе (pre-fill) и пишет на выходе (экспорт результата).
- Глобальный state-manager (Redux/Zustand/XState) **не используется** без явного пересмотра этого документа. Если конкретный модуль (например, ПЗ7 с несколькими синхронными виджетами — шахматка + оптимизатор + график) не тянет на Context — это отдельное точечное решение по этому модулю, а не пересмотр архитектуры всего приложения.

## Запрещено

- Хранить бизнес-логику/формулы внутри JSX или компонентов — только в `shared/lib`, с тестом рядом.
- Использовать `any`. Если тип неизвестен на момент разбора методички — `unknown` и явный `// TODO: уточнить по методичке`, не заглушка `any`.
- Хранить состояние нескольких шагов модуля в одном неструктурированном `useState`-объекте — использовать типизированный Context.
- Импортировать код одного ПЗ в другой напрямую.
- Добавлять глобальный state-manager без явного решения, зафиксированного в этом файле.
- Предлагать бэкенд/БД/авторизацию/роли — уже решено, что их нет; это ограничение нарушают чаще всего.

## Canvas UI — ограничения под iSpring iframe

- Web Object в iSpring — **прямоугольная форма фиксированного размера**, автор курса растягивает её вручную в редакторе (либо открывает в отдельном окне браузера с явно заданными размерами). Мы не управляем итоговым размером контейнера программно.
- Закладывать разумный минимальный размер (ориентир — 16:9 от ~960×540) и деградацию вёрстки при более тесных пропорциях, не только `overflow-hidden` в расчёте на «как получится».
- iframe кросс-доменный → `postMessage` единственный легальный канал наружу. Поддержка авто-resize плеером iSpring через `postMessage`/`ResizeObserver` **не подтверждена** — риск, `overflow-hidden` — надёжный минимальный вариант без внешней поддержки.
- Никаких форм регистрации/логина, глобальных футеров, тяжёлых хедеров. Компактная вёрстка, внутренние списки скроллятся изолированно (`overflow-y: auto`), без двойного скролла.
- Роли пользователей не проектируются — распределение ролей внутри команды происходит вне приложения, даже если упомянуто в методичке ПЗ1.

## Навигация и последовательность (не выводится из картинок — читать буквально)

- Прохождение **строго линейное вперёд**: интро → теория → задание (шаг 1 → шаг 2 → … ) → итог. Нельзя прыгнуть на шаг, который ещё не открыт («заблокированное» будущее).
- Прогресс-трасса — единственный навигационный элемент. Никакого отдельного сайдбар-меню или второго списка шагов рядом — это дублирование одного и того же состояния разными виджетами, чего быть не должно (см. design-reference.html, блок «locked-future»).
- По уже пройденным шагам **можно** вернуться назад (кликом по пройденной станции на трассе), но нельзя перепрыгнуть вперёд через непройденный шаг.
- Теория — не отдельная точка маршрута, а **overlay поверх текущего шага задания**, открывается/закрывается кнопкой, не меняет URL/фазу. Явно смотрится один раз при первом входе, дальше доступна по кнопке в любой момент.
- Экран «Итог» — это сводка для человека (варианта, счётчиков, кнопок «Скачать JSON» / «Скачать PDF»), **не** сырой дамп JSON на экран. Внутреннее состояние моста никогда не показывается студенту как текст/код — оно только скачивается файлом.

## Design reference — статус покрытия

`docs/design-reference.html` — это НЕ полный дизайн-кит, а растущий набор образцов. Открывающий его должен свериться со списком покрытия в самом файле (комментарий вверху) прежде чем достраивать недостающее по своей интуиции — недостающее нужно спросить, а не досочинить.

## Сквозные UX-требования (со встречи с заказчиком — касаются всех 8 модулей)

- **Кнопка сохранения на каждом этапе.** Не только на экране «Итог» — на каждом шаге своя кнопка перезаписи/сохранения результата. Снижает потерю данных при закрытии вкладки.
- **«Живой» итоговый экран.** Итог не является замороженным снимком: студент может вернуться назад, изменить входные данные и увидеть пересчитанный результат. Следствие для архитектуры: **итоговые показатели должны быть производными (вычисляемыми) от состояния модуля, а не сохранёнными значениями.** Не кэшировать результат при переходе на «Итог».
- **Тултипы-«i» у показателей.** У каждого расчётного показателя — иконка «i» с пояснением, что означает величина. Особенно в блоке 13 итоговых показателей ПЗ1.
- **Валидация значений** — на каждом числовом поле, с разделением на блокирующую и предупреждающую (образец правил — `pz1-copy-and-validation.md`).
- **Цветовые шкалы для индексов.** Где показатель — индекс 0..1 с направлением «лучше/хуже» (коэффициент дискомфорта в ПЗ1), использовать цвет: 0 = зелёный, 1 = красный. Не оставлять голое число.
- **Удаление столбцов в таблицах.** Где столбцы = сущности, которых может не быть в конкретном случае (виды транспорта между парой станций) — столбец должен удаляться.
- **Русская типографика — неразрывные пробелы.** Одно- и двухбуквенные предлоги и союзы (в, к, с, на, по, от, из, и, а) не должны оставаться в конце строки — переносятся на следующую строку вместе со следующим словом. Реализация: `&nbsp;` после короткого слова, либо утилита-обёртка для отображаемого текста. Применяется ко всем текстам интерфейса и к PDF-отчёту.

## Модель модуля (оболочка)

Единый жизненный цикл для всех 8 модулей:

```
интро (паспорт / вариант / импорт JSON)
  → теория (интро-проход + переоткрываемая панель поверх задания)
  → задание (массив шагов — не один слот)
  → итог (экспорт в мост + PDF)
```

Фаза «задание» — массив шагов, потому что методички разнотипны: ПЗ5 — два независимых блока в одном модуле, ПЗ1 — многошаговый с повтором расчёта на каждую корреспонденцию, ПЗ7 — два блока со своими под-шагами.

## Таксономия типов шага (`kind`)

Выведена из разбора всех 8 методичек, каждый тип прототипирован и визуально проверен. Примеры конкретных ПЗ — см. [pz-specs.md](./pz-specs.md).

| `kind` | Что это |
|---|---|
| `data-entry` | Открытые поля-бланки |
| `data-entry-hint` | Поле с постоянно видимой справочной подсказкой-диапазоном рядом (не placeholder, не tooltip) |
| `interactive-table-variant` | Параметр × N вариантов, назначенный вариант подсвечен (ПЗ4, ПЗ5, ПЗ6 — все три автономны именно благодаря этому шагу) |
| `interactive-table-matrix` | Симметричная шахматная таблица откуда/куда, диагональ заблокирована |
| `interactive-table-optimizer` | Таблица с редактируемыми значениями и живым пересчётом производных показателей + цветовая подсказка |
| `table-calculator-hybrid` | Таблица результатов, каждая строка — своя формула, есть строка «Итого» |
| `calculator` | Цепочка формул; шаг может использовать результат предыдущего шага внутри того же ПЗ |
| `drag-drop-map` | MapLibre-карта. Два раздельных набора: станции (метки, лимит 2 терминала + max 2 промежуточных) и вершины линии трассы (waypoints, БЕЗ лимита, редактируемый polyline, НЕ автогенерируется из станций). Детали — pz-specs.md, ПЗ1 |
| `drag-drop-scheme` | Готовая (не процедурная) SVG-подложка схемы + интерактивный слой с заранее размеченными валидными точками |
| `scheme-reader` | Готовая схема для чтения + производный расчёт (ничего не двигают) |
| `survey-constructor` | Конструктор анкеты + сбор/анализ ответов |
| `control-questions` | Короткие текстовые ответы на вопросы понимания |
| `schedule-graph` | График движения поездов, курсор для подсчёта пересечений |

**Важно про `drag-drop-scheme`:** реальные схемы станций (ПЗ5) — 4–5 параллельных путей с лестницей стрелочных переводов. Подтверждено визуальным просмотром PDF: сигналы добавляются послойно на одну и ту же схему, похоже на одну базовую топологию станции, не набор разных схем под варианты. Решение: не писать процедурный генератор произвольных станционных схем — вручную перерисовать 1–2 реальные схемы в SVG (тот же паттерн, что карта ПЗ1: готовая подложка + клики поверх), с заранее размеченными точками посадки по типу сигнала.

## Мост и персистентность

Единый накапливающийся JSON-файл, не отдельный на каждое ПЗ. Файл несёт **две разные роли**, не смешивать:

- `completed` — межмодульный мост: готовые результаты завершённых ПЗ, пред-заполняют вход следующего модуля
- `progress` — персистентность **внутри** модуля: незавершённая работа, позволяющая продолжить с того же экрана

```ts
interface Passport {
  team: string;
  lineTitle: string;
  defaultVariant?: number;
  createdAt: string; // ISO 8601
}

interface ModuleProgress<TDraft = unknown> {
  currentStepId: string;   // на каком шаге сохранились — по stable id, не по номеру позиции
  draft: TDraft;           // черновые значения по всем начатым шагам, могут быть неполными
  savedAt: string;         // ISO 8601
}

interface BridgeSchema {
  // 1.2 — добавлена секция текущего строительного модуля. Файлы 1.0 и 1.1
  // читаются по-прежнему; старый ключ pz2 преобразуется в pz3 при импорте.
  schemaVersion: '1.0' | '1.1' | '1.2';
  passport: Passport;
  completed: Partial<{
    pz1: Pz1Result; pz3: Pz3Result; pz4: Pz4Result;
    pz5: Pz5Result; pz6: Pz6Result; pz7: Pz7Result; pz8: Pz8Result;
  }>;
  progress?: Partial<{
    pz1: ModuleProgress<Pz1Draft>; pz3: ModuleProgress<Pz3Draft>; /* … pz4…pz8 */
  }>;
}
```

**Принцип моста (`completed`):** только пред-заполняет входы следующего модуля, никогда не блокирует. Каждый ПЗ автономен — при отсутствии данных сверху работает ручной ввод/выбор варианта. Команды могут проходить ПЗ не по порядку.

### Персистентность (`progress`) — решение заказчика, зафиксировано дословно

> «Прогресс должен подписываться из JSON-файла и сохраняться туда же в любой момент работы через кнопку, и должен будет открываться тот же экран (задание), на котором JSON был сохранён с уже введёнными значениями (если задание уже было начато). Никаких Google Forms и т.д.»

**Единственный носитель — файл.** Не localStorage, не сервер, не загрузка по идентификатору. Это сохраняет ОТ-1 (нет бэкенда) без исключений.

- **Кнопка сохранения — на каждом шаге** (`ФТ-19`), не только на «Итоге». Пишет весь `BridgeSchema`, включая незавершённый текущий шаг, через `bridge/io.ts` (скачивание `Blob`).
- **Загрузка** — на интро модуля (`<input type="file">`), студент выбирает свой файл вручную. Браузер не может «сам найти», где сохранились — это всегда явный выбор файла.
- **Восстановление места** — при загрузке файла с `progress.pzN` открывается шаг `currentStepId`, а не начало модуля; поля этого и всех пройденных шагов заполнены значениями из `draft`.
- **Каждый ПЗ обязан работать с чистого листа** — загрузка файла удобство, не обязательный вход (согласуется с `ФТ-16`).

**Механизм в браузере — не тривиален, два реальных риска:**
1. Скачивание и `<input type="file">` внутри Web Object iSpring могут вести себя иначе, чем на обычной странице (sandbox-атрибуты iframe). **Не подтверждено на живом плеере** — проверить до финализации, тот же класс риска, что `postMessage` (см. `ИТ-7`).
2. UX множественных сохранений: каждое нажатие «Сохранить» — новый файл в «Загрузках» браузера (`progress (1).json`, `(2).json`…). Продумать имя файла и явную инструкцию студенту грузить именно последний.

**Реализация — за абстракцией**, компоненты не трогают файловую систему напрямую: `bridge/io.ts` инкапсулирует чтение/запись `BridgeSchema` целиком (и `completed`, и `progress`). Отдельного класса/интерфейса `DraftStorage` в коде заводить не нужно — это то же самое, под другим названием использованное в `ТЗ v3.x`; если это название встретится в других документах команды, читать как синоним `bridge/io.ts` + `progress`-поле схемы, не как отдельную нереализованную сущность.

### Граф зависимостей (проверено по методичкам — версия 2)

- ПЗ1 → ПЗ3: **сильная** для реализованного строительного модуля. Фактически переносятся:
  - паспорт проекта (учебная группа, вариант);
  - **длина маршрута** — эталон, с которым ПЗ3 сверяет сумму длин работ;
  - геометрия трассы и станции — по ним ПЗ3 рисует карту и меряет участки линейкой.
  Без файла ПЗ1 строительное задание не начинается: мерить нечего и сверять не с чем.
- ПЗ1 → ПЗ7: матрица корреспонденций, размер динамический по числу станций ПЗ1 (2–4)
- ПЗ4, ПЗ5, ПЗ6, ПЗ8: **автономны** по прежним методичкам; для будущих модулей зависимости нужно уточнить после пересмотра нумерации.

## Модель варианта задания

- `passport.defaultVariant?` — если преподаватель называет один номер на весь семестр
- Свой `variants.ts` со статическими пресетами в модулях, где методичка задаёт вариантный набор — подтверждено для ПЗ1 (6 направлений), ПЗ5 и ПЗ6 (единый формат таблицы, 10 вариантов)
- Не универсально для всех 8 — где вариантов нет, ручной ввод/данные из предыдущего модуля
- Модуль может переопределить `defaultVariant`, если у него своя нумерация

## PDF-отчёт

Собирается на клиенте (`@react-pdf/renderer`), студент видит по завершении, скачивает и сдаёт вручную. Никакой БД на бэкенде.

**Гранулярность:** отдельный PDF на каждое ПЗ (кнопка на экране «Итог») + опциональная сборка всех в один комбинированный отчёт.

**Архитектура:** `generatePzReport(pzId, result, passport)` — одна функция на ПЗ; `generateCombinedReport(bridge)` вызывает её для каждого заполненного `completed.pzN` и склеивает в один `<Document>` — один шаблон, не два рендер-пути.

**Три категории контента:**
1. Числа/текст — рендерятся напрямую, без сложностей
2. Формулы — `@react-pdf/renderer` не рендерит KaTeX нативно. Рендерить в PNG на клиенте (offscreen canvas), сохранять как часть результата шага. Момент рендера (при завершении шага vs при экспорте) — см. open-questions
3. Визуальные шаги (карта, схема) — каждый визуальный `kind` обязан отдавать `previewImage: string` (base64 PNG) как часть результата шага — контракт зафиксировать до кодирования ПЗ5

**Черновая структура одного PZ-отчёта:** титул (линия, команда, ПЗ, вариант, дата) → секция на каждый шаг → контрольные вопросы отдельным блоком в конце.

## Требования к передаче кода

Применимо ко всему проекту, не только к ПЗ1 (см. `НФТ-7` в `SRS.md`). Заказчик прямо запросил получить код после оплаты, планирует использовать много лет — переписывать по ГОСТам не требуется, но закладывать это нужно сейчас, не в конце:

- Осмысленные имена переменных/функций/файлов — без мусорных и шуточных
- Сборка с нуля по README, без устных пояснений
- Никаких секретов в коде и в git-истории (ключи внешних сервисов — например MapTiler — ограничивать по домену в панели провайдера, не полагаться на «просто не коммитить»)
- `CONTRIBUTING.md` и `docs/` актуальны
- Тесты на расчётных функциях — они же документация к формулам
- Комментарии там, где логика неочевидна (геометрия трассы, модель прогноза)

## Тестовая стратегия

**Тестируем:**
- все расчётные функции в `shared/lib` — на примере из `docs/examples/pzN.md`
- парсинг и валидацию bridge (`bridge/schema.ts`, `bridge/io.ts`)
- миграции `schemaVersion`
- генерацию PDF — структурно (правильные секции/данные попали в документ), не пиксель-в-пиксель
- валидаторы вариантов (`variants.ts`)

**Не тестируем:** CSS, анимации, точную вёрстку.
